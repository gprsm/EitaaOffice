# مدل پیشنهادی پرسشنامهٔ برنامه و تکمیل حلقه‌های داده

وضعیت: `DOMAIN_PROPOSAL / IR-0-B_INPUT / NOT_IMPLEMENTED`  
تاریخ پیشنهاد کاربر: 2026-08-27  
Source: `SRC-USER-IR-004`  
Finding: `F-058`

## مسئله

workbook خروجی تجمیعی می‌خواهد، اما دادهٔ لازم ممکن است در زمان‌ها و منابع مختلف برسد: خبر اولیه، عکس، تعداد شرکت‌کنندگان، اطلاعات مالی، فهرست افراد، دادهٔ پایهٔ واحدها، نرخ‌های مفروض و محاسبات استنباطی. یک label روی پیام نمی‌تواند این حلقه را کامل کند.

پیشنهاد کاربر این است که هر برنامهٔ کلی workbook به یک پرسشنامه/فرم الکترونیکی تبدیل شود تا داده‌های پراکنده به موضوع، رویداد، واحد و دورهٔ درست متصل شوند. صورت نرمال‌شدهٔ پیشنهاد، «تعریف نسخه‌دار پرسش‌ها و پاسخ‌های گزارش‌پذیر» است؛ UI فرم فقط یکی از روش‌های ورود به این مدل خواهد بود.

## الگوی پایهٔ مشترک

هر برنامه از یک هستهٔ مشترک و یک ماژول اختصاصی تشکیل می‌شود.

### بخش A — زمینهٔ گزارش

- نسخهٔ چارچوب و دورهٔ گزارش؛
- استان، ستاد استانی و واحد/حوزهٔ شهرستانی؛
- برنامه، زیرجدول و metricهای هدف؛
- وضعیت پاسخ: draft، ناقص، نیازمند بررسی، تأییدشده یا superseded.

### بخش B — رویداد یا موضوع

- رویداد/فعالیت چیست، چه زمانی و کجا رخ داده است؛
- واحد مجری، همکاران، مخاطبان و مناسبت؛
- نقش رکورد: رخداد اصلی، اقدام پشتیبان، اطلاع‌رسانی، مدرک، اصلاح یا گزارش تجمیعی؛
- اتصال چند پیام/رسانه/سند به یک رویداد بدون ادغام قطعیِ زودهنگام.

### بخش C — شواهد

- خبر/متن، عکس/فیلم، دعوت‌نامه، مکاتبه، فهرست، بیمه، قرارداد، نظرسنجی و فایل مالی؛
- مرجع Provider/account/message یا سند دستی با authorization؛
- کفایت مدرک برای هر metric جداگانه سنجیده می‌شود. وجود عکس به‌تنهایی عدد شرکت‌کننده یا تحقق همهٔ شروط را ثابت نمی‌کند.

### بخش D — داده‌های مستقیم

- تعداد رخداد، شرکت‌کننده، تقدیرشونده یا اقدام؛
- مقدار، واحد اندازه‌گیری، زمان و دامنه؛
- `value_kind`: `observed`، `reported_by_unit`، `estimated`، `synthetic_placeholder` یا `verified`؛
- منبع، عامل ورود، زمان ورود و تاریخچهٔ اصلاح.

### بخش E — داده‌های مالی

- مبلغ و نوع هزینه، منبع تأمین، دوره و رویداد مربوط؛
- مبلغ اعلامی/سندی از مبلغ برآوردی جداست؛
- سند مالی و سطح دسترسی مستقل از خبر عمومی نگه‌داری می‌شود.

### بخش F — داده‌های پایه و مرجع

- فهرست واحدهای فعال و تعداد کارکنان هر واحد/گروه مخاطب؛
- تقویم مناسبت‌ها و طبقهٔ بزرگ/کوچک یا قواعد eligibility؛
- ظرفیت، نرخ پوشش و سایر پارامترهای دوره‌ای؛
- هر مقدار دارای نسخه، دورهٔ اعتبار و منبع است.

### بخش G — فرض‌ها و پارامترها

- نرخ اجرای برنامه در واحدها؛
- نرخ حضور برای نوع مناسبت یا گروه مخاطب؛
- قواعد جایگزینی مقدار مفقود؛
- فرض با fact مخلوط نمی‌شود و تغییر نسخهٔ آن باید تمام خروجی‌های وابسته را قابل بازتولید نگه دارد.

### بخش H — مقادیر مشتق‌شده

هر مقدار مشتق‌شده باید formula/version، ورودی‌ها و provenance خود را داشته باشد. نمونهٔ مفهومی:

```text
estimated_event_count
  = eligible_occasion_count
  × eligible_unit_count
  × execution_rate

estimated_attendance
  = Σ(unit_employee_base × event_specific_attendance_rate × eligible_event_count)
```

این فرمول‌ها صرفاً مثال‌اند و تا تعریف eligibility، جلوگیری از هم‌پوشانی و نرخ‌های معتبر، قاعدهٔ اجرایی نیستند. مقدار دقیق/تأییدشده در دامنهٔ همسان بر مقدار برآوردی اولویت دارد؛ جایگزینی باید audit شود.

### بخش I — بازبینی و projection

- چه پاسخ‌هایی ناقص یا متعارض‌اند؛
- کدام factها اجازهٔ ورود به aggregation دارند؛
- breakdown رویداد/شهرستان و عدد تجمیعی استان؛
- projection به workbook، WordPress یا گزارش تفصیلی بدون تغییر source evidence.

## ماژول اختصاصی هر برنامه

هستهٔ بالا مشترک است، اما سؤال‌ها و قواعد هر برنامه متفاوت‌اند:

| برنامه | نمونهٔ محور اختصاصی |
|---|---|
| اردو | نوع اردو، شرکت‌کنندگان، خودرو، بیمه، پذیرایی، هزینه، فهرست و سین برنامه |
| مسابقات | نوع/رشته، طراحی سؤال، داوری، برگزیدگان، جامعهٔ مخاطب و بانک اطلاعاتی |
| مراسم | نوع مناسبت، مراسم اصلی، زیارت عاشورا، نشست واجد شرایط، فضاسازی، مداح/سخنران و بستهٔ فرهنگی |
| اقامه نماز | جشن تکلیف، نومکلفان، ائمه جماعت، نمازخانه‌ها، قرارداد و بانک اطلاعاتی |
| تکریم | استقلال مراسم، مقام حاضر، مناسبت، تقدیرشوندگان و تولیت مشترک |
| تشویق | معیار رضایت ارباب رجوع، برگزیدگان، مقام حاضر و بانک اطلاعاتی |
| منشور | مکاتبه، نصب تابلو، بازنشر، آموزش/نشست/مسابقه و بازنگری حاصل از نظرسنجی |

فهرست نهایی سؤال‌ها فقط پس از بستن ابهام‌های workbook و نگاشت metricها نوشته می‌شود.

## نمونهٔ چرخهٔ اردو

1. پیام یا خبر، وجود احتمالی اردو را به‌عنوان claim ایجاد می‌کند.
2. عکس/گالری و دعوت‌نامه به همان رویداد candidate متصل می‌شوند.
3. پاسخ بعدی واحد می‌تواند تعداد شرکت‌کنندگان را با `reported_by_unit` تکمیل کند.
4. سند مالی با سطح دسترسی مناسب، هزینه را به همان event وصل می‌کند.
5. اگر عددی موجود نباشد، formula می‌تواند مقدار `estimated` تولید کند؛ این مقدار verified نیست.
6. پس از review، رویدادهای واجد قاعده به metric استانی دوره افزوده و breakdown قابل مشاهده باقی می‌ماند.

## نمونهٔ محاسبهٔ مراسم

داده‌های پایهٔ پیشنهادی کاربر—تعداد مناسبت مذهبی/ملی، تعداد واحدها، نرخ اجرای واحدها، تعداد کارکنان هر واحد و نرخ حضور برحسب بزرگی مناسبت—می‌توانند estimate قابل‌بازتولید بسازند. برای جلوگیری از گزارش گمراه‌کننده باید:

- مناسبت eligible و واحد eligible صریح باشند؛
- نرخ ۹۰٪ به denominator مشخص متصل باشد؛
- نرخ حضور به نوع مناسبت، واحد و دوره نسخه‌دار باشد؛
- رویداد واقعی گزارش‌شده جای estimate متناظر را بگیرد، نه اینکه با آن دوباره شمرده شود؛
- نتیجه با برچسب `estimated`، formula و ورودی‌هایش نمایش یابد؛
- زیارت عاشورا metric جدا باشد و شمارش اصلی مراسم را افزایش ندهد.

## workflow پذیرفته‌شدهٔ تکمیل

Q-IR-014 با `SRC-USER-IR-005` بسته شد:

1. واحدهای شهرستانی اطلاعات را فقط از طریق Eitaa ارسال می‌کنند و کاربر سامانه نیستند.
2. خبرهای ستاد نیز می‌توانند از Eitaa وارد جریان evidence و در صورت review به WordPress منتقل شوند.
3. سامانهٔ محلی از Eitaa/WordPress پاسخ‌های candidate و شکاف‌های پرسشنامه را پیشنهاد می‌کند.
4. فقط کاربر اصلی و همکاران ستادی مجاز در یک مکان فیزیکی/شبکهٔ خصوصی، پاسخ‌ها را تکمیل و اصلاح می‌کنند.
5. اتوماسیون یادگیرندهٔ محلی مسیر ترجیحی کمک است؛ API عامل هوشمند فقط fallback اختیاری با privacy/budget/review است.
6. تأیید نهایی، محاسبات استانی و export گزارش به نقش انسانی مرکزی مجاز منتسب می‌شود؛ هیچ Agent یا پیشنهاد خودکار approver نیست.

این تصمیم workflow دامنه است، نه پیاده‌سازی دسترسی. LAN جای authentication، role، audit یا server-side authorization را نمی‌گیرد.

## معیار پذیرش آینده

- هر سؤال به metric یا evidence requirement مشخص نگاشت شود؛
- سؤال مشترک فقط یک تعریف canonical داشته باشد؛
- تغییر فرم با version انجام شود و پاسخ تاریخی باقی بماند؛
- مقدار مشتق‌شده تا ورودی‌ها و formula قابل trace باشد؛
- exact/reported/estimated/synthetic/verified قابل تفکیک باشند؛
- aggregation بدون double count و با breakdown قابل بازتولید باشد؛
- سطح دسترسی اسناد مالی/شخصی از خبر و media عمومی مستقل باشد؛
- واحد شهرستانی account/role سامانه نداشته باشد؛
- هر تأیید و export به کاربر انسانی مرکزی مجاز و audit متصل باشد.
