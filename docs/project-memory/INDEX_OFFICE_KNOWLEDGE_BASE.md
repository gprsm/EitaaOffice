# پایگاه دانش محصول دفتر (EitaaOffice) — مرجع فشردهٔ دامنه و معماری

وضعیت: `PRODUCT_KNOWLEDGE_BASE / v1 (2026-09-27)`  
منابع: F-087 تا F-091، ADR-53/55/61، V-218 تا V-222، سند طراحی پوسته (`INDEX_SECTION_SHELL_DESIGN.md`)، ژانرهای سند (`reporting-document-genres` حافظه)، کاربرگ ۱۴۰۵ (SRC-IR-001)، کاربرگ بازدید استانی، فرم بومی ستاد اقامه نماز، فایل وضعیت‌سنجی، پوشهٔ Report کاربر.

## ۱. اصل بنیادین (دال محوری)

مرکز مدل، **فعالیت‌های خود اداره** است. هر مرجع بیرونی (کاربرگ ۱۴۰۵ مرکز، کاربرگ بازدید استانی، فرم بومی ستاد اقامه نماز، دستگاه مرکزی) فقط یک مجموعه شاخصه است که به همان فعالیت‌ها نگاشت می‌شود. تکلیف تازه = نگاشت تازه، نه ساختار تازه. تعارض شاخصه‌ها در لایهٔ نگاشت حل می‌شود، نه در داده.

## ۲. زنجیرهٔ مدل

```text
ابلاغ ← بخش (section) ← طرح (campaign) ← رویداد (event) ← فکت/مدرک
رجیستری‌های پایه: واحد، امام جماعت، نمازخانه، نومکلف، شخص (کارمند/خانواده)
فکت‌ها: رویدادی (Fact) + رجیستریِ دوره‌ای (EntityFact: unit/venue/imam/nomokalaf/section)
```

- هر کمیت یک metric در فرهنگ دادهٔ نسخه‌دار (`office-metrics-v2`، ۸۶ metric) است.
- مقدارها همیشه `value_kind` دارند: observed / reported_by_unit / estimated / synthetic_placeholder / verified (ADR-42: دوتای آخر هرگز export-ready نیستند).
- عامل/اسکریپت فقط «پیشنهاد» می‌دهد (صف کاندید)؛ تأیید نهایی فقط انسانی (Q-IR-014).

## ۳. دوازده بخش گزارش (داده، نه enum)

هفت برنامهٔ کاربرگ ۱۴۰۵: اردو 80401، مسابقات 80402، مراسم 80403، نماز 80501، تکریم 80406، تشویق 80601، منشور 80202.  
پنج محور تکمیلی کاربرگ بازدید: دوره/کارگاه آموزشی، تولید محتوا، خدمات مشاوره، خدمات تحصیلی فرزندان، تعامل برون‌سازمانی.  
کتابکد: شناسهٔ داخلی مرجع است؛ کد رسمی هر سند نگاشت است (تضاد 80402/80403 دو سند رسمی — ADR-61).

## ۴. پروجکشن‌های شناخته‌شده (از یک مخزن)

1. کاربرگ سالانه ۱۴۰۵ (ستون‌های ستاره‌دار) — `excel_export`.
2. کاربرگ بازدید استانی — `projections.build_visit_worksheet_prayer_row` + dossier.
3. کاربرگ دوماهه عددی (اول/دوم/سوم) — فکت‌های section@1405-P1/P2/P3؛ ستاره‌های درج‌نشده در فایل ارسالی = شکاف واقعی.
4. قالب گزارش عملکرد روایی-مالی (اقدامات/نتایج/موانع/راهکارها/مستندات/اعتبار-هزینه‌کرد؛ ترتیب: سند تحول → ذاتی → شاخص) — `NARRATIVE_REPORT_FORM` + فکت‌های program_obstacles/program_proposals/allocated_budget/spent_budget.
5. پروندهٔ بازدید استانی (senario آزمون عامل) — `build_prayer_dossier`.

## ۵. خط تولید واقعی داده (از کورپوس Report آموخته شد)

رویداد در ایتا/واقعیت → خبر وردپرس (post.html + تصاویر؛ ۱۰۵ رویداد وارد شده) → بایگانی دوره/برنامه → گزارش تجمیعی → کاربرگ دوماهه → مرکز. پیوند پست↔رویداد در جدول `wp_post_links` با وضعیت auto/candidate/unmatched نگه داشته می‌شود.

## ۶. داده‌های واردشده تا امروز (پایگاه عملیاتی data/reporting/reporting.sqlite3)

- وضعیت‌سنجی ۱۴۰۵: ۳۱ واحد یکتا (فایل منبع «دادسرای ساری» را دوبار دارد — نیازمند تصمیم اپراتور)، ۳۹۲ فکت، ۷۸ کاندید صف نرمال‌سازی/امام.
- کاربرگ‌های دوماهه اول/دوم/سوم: ۵۳ فکت عددی + ۲۶ ستارهٔ معلق (شکاف) + پاسخ‌های متنی آزاد.
- کورپس وردپرس: ۱۰۵ رویداد legacy-import با ۱۰۵ نظرسنجی مصنوعیِ باورپذیر (`synthetic_placeholder` — هیچ‌گاه آمار تأییدشده نمی‌شوند) و ۱۰۹ پیوند پست.
- اشخاص: ۵۲ رکورد یکتا (کارمندان نمونه ۱۴۰۴، حاضران اردوی سوادکوه با تماس، قرعه‌کشی کربلا/مشهد) + رویداد اردوی سوادکوه ۱۴۰۵/۰۳/۲۱.
- رویدادهای پیشین برنامه (V-196/V-218 pipeline) نیز در همان مخزن‌اند.

## ۷. مرزها و قواعد حریم خصوصی

- کد ملی/شماره تماس/شماره پرسنلی و نام‌ها فقط در پایگاه محلی می‌مانند؛ پروجکشن‌ها و گزارش‌ها فقط شمارش تجمیعی.
- سند مالی از خبر عمومی جداست.
- دادهٔ مصنوعی همیشه برچسب و seed دارد و بازتولیدش سرجایگزین است.
- push فقط به مخزن EitaaOffice؛ مخزن اصلی EitaaDesktop دست‌نخورده.

## ۸. نقشهٔ محصول (چیزی که فردا تحویل می‌شود)

- تب «داشبورد دفتر» در کارتابل گزارش: کارت‌های دوازده بخش با تحقق و شکاف، صف تأیید انسانی (نرمال‌سازی + پست‌های بی‌پیوند)، پروندهٔ بازدید.
- API: `/api/v3/office/{sections,registry,queue,queue/{id}/review,dossier,bimonthly,wp-links}`.
- فاز بعدی کوت‌مدت: مهاجرت ۷ فرم کاربرگ به بخش‌محور کامل، خروجی‌ساز کاربرگ دوماهه از فکت‌ها، ویرایش رجیستری اشخاص در UI، اتصال زندهٔ رصد ایتا به طرح‌ها.
