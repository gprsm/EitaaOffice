# گزارش زیرساخت اتصال سامانهٔ آموزش/آزمون — اعتبارسنجی مستقل و تکمیل

تاریخ: ۲۰۲۶-۰۹-۲۷
شناسه‌ها: F-083 (ادعای اولیه)، F-084 (یافته‌های اعتبارسنجی مستقل)، V-213 (اعتبارسنجی ادعایی)، V-214 (اعتبارسنجی پس از اصلاح)، ADR-59
مرزهای درخواستی: (۱) API ماشین‌به‌ماشین با مجوز محدود، (۲) بررسی گیرنده و ارسال پیام متنی از حساب مجاز ایتا و پس از پیش‌نیازها بله، (۳) درگاه backend برای گفت‌وگوی کاربران سایت با عامل هوشمند.

## ۱. خلاصه

ادعای جلسهٔ پیش (F-083/V-213) مبنی بر «۳۱ آزمون سبز و کنترل‌های کامل» با اجرای مستقل آزموده شد. چهار فایل آزمون جدید واقعاً ۳۱/۳۱ سبز بودند، اما مجموعهٔ کامل Backend **هفت شکست** داشت که گزارش نشده بود:

| شکست | ریشه |
|---|---|
| `test_phase5_shared_contacts` (500 به‌جای 400) | باگ scoping پایتون: `from ..errors import CompositionValidationError` درون شاخهٔ M2M، نام را برای کل تابع dispatch محلی می‌کرد؛ بررسی forged-field v1 با `UnboundLocalError` می‌مرد |
| سه آزمون ارتقای اسکیما (v6/v5/v4) | انتظار نسخهٔ ۷؛ تنزل آزمایشی artifacts v8 را حذف نمی‌کرد |
| نگهبان transport بله (F-046/G-02) | بستهٔ `providers/bale_bot` با import مستقیم `httpx` قرارداد درخت providers را می‌شکست |
| کاتالوگ رخدادها | سه رخداد `service_credential_*` ثبت نشده بودند |
| parity ویل | فایل‌های جدید به wheel اضافه نشده بودند |

همچنین بازبینی کد سه نقص ماهوی آشکار کرد که با آزمون‌هایFake پوشیده مانده بود:

1. **resolve ساختگی**: هر مقدار بدون پسوند «9999» با `peer_reference` جعلی «resolved» اعلام می‌شد؛ در حالی که مسیر ارسال واقعی ایتا شناسهٔ گفتگو (`user:<id>`) می‌خواهد و شمارهٔ خام به `api_dialog_not_found` می‌رسید.
2. **پنل UI غیرعملیاتی**: هیچ فراخوانی API نداشت و توکن هاردکد قلابی نشان می‌داد.
3. **نقاط ضعف ثانویه**: دور زدن scope در agent chat برای `service_name == "test"`، نقش `admin` برای عامل سرویس، اعمال‌نشدن `allowed_providers`، بازگرداندن توکن قلابی در rotate ردیف ناموجود، و DoS PBKDF2 بدون throttle پیش از احراز.

## ۲. اصلاحات انجام‌شده

- `src/eitaa_bridge/application/api.py`: حذف importهای درون‌تابعی (رفع رگرسیون v1)، throttle پیش از تأیید توکن (۳۰ شکست در ۶۰ ثانیه → 429 `m2m_auth_throttled`)، جداسازی Bearer قدیمی از مسیر M2M، خطای 404 برای rotate ناموجود، `peek_runtime_for_account` فقط‌خواندنی برای resolve بدون اجرای ناخواستهٔ worker.
- `src/eitaa_bridge/application/m2m_api.py` بازنویسی صادقانه: resolve فقط‌خواندنی واقعی (دایرکتوری مخاطبین مشترک + کاتالوگ گفتگوی حسابِ زنده؛ خروجی فقط `value_hash`، بدون بازگرداندن شمارهٔ خام)، منع شمارهٔ خام/username به‌عنوان peer با `409 m2m_recipient_unresolved`، اعمال `allowed_providers`، نقش کم‌امتیاز `user`، حذف دور زدن scope، مهار استعلام وضعیت به حساب‌های مجاز اعتبارنامه، اعتبارسنجی فرمت کلید پایاپای.
- `src/eitaa_bridge/infrastructure/coordinator/service_credentials.py`: rotate ردیف ناموجود/ابطال‌شده را با خطا رد می‌کند.
- `src/eitaa_bridge/providers/bale_bot/`: حذف فایل اسکرچ `_offline_tests.py`؛ پاک‌سازی آداپتور (ثابت endpoint رسمی، حذف سایه‌گذاری پارامتر manifest)؛ همچنان ثبت‌نشده در registry و fail-closed.
- آزمون نگهبان `test_bale_slot_has_no_transport_dynamic_loader_or_endpoint_literal`: carve-out مستند برای bale_bot (فقط `httpx`، بدون importlib/pkgutil/raw_rpc، سقف یک endpoint رسمی) با حفظ کامل قواعد `providers/bale/`.
- Event Catalog: ثبت `service_credential_created/revoked/rotated` (audit_required).
- آزمون‌های بله‌بات به `tests/test_bale_bot_adapter.py` منتقل شدند (۶ آزمون شامل fail-closed بودن ثبت) و سه آزمون اسکیما به v8 به‌روزرسانی شدند.
- `ui/src/ServiceAccountSettingsPanel.tsx` بازنویسی کاربردی: اتصال به `GET/POST /api/v2/service-credentials` و rotate/revoke، نمایش توکن فقط یک‌بار، انتخاب دامنه‌ها و حساب‌های واقعی، چیپ وضعیت از `provider_adapters`.
- wheel با اسکریپت رسمی بازسازی شد (SHA-256 `0b3efebd…347b4fb7`).
- قرارداد به نسخهٔ **1.1.0** ارتقا یافت: مالکیت داده، احراز هویت، قرارداد عملیات‌ها، وضعیت‌های رسید، قواعد retry، محدودیت‌های Provider و راهنمای پیکربندی.

## ۴. جدول وضعیت مستقل

| قابلیت | طراحی‌شده | پیاده‌سازی‌شده | آزموده‌شدهٔ آفلاین | پذیرفته‌شدهٔ واقعی |
|---|---|---|---|---|
| ارسال ایتا از حساب مجاز (M2M) | ✔ (قرارداد 1.1.0) | ✔ (از orchestrator عمومی) | ✔ (Fake/Contract) | ✖ — نیازمند حساب زنده و دروازهٔ پذیرش |
| ارسال بله (Bot) | ✔ (ADR-59) | داربست؛ ثبت‌نشده در registry | ✔ (آفلاین آداپتور) | ✖ — تا مستندات/توکن رسمی مالک و دروازه‌ها |
| ارسال بله شخصی | ✔ (F-086/ADR-60) | ✔ آداپتور واقعی + رفع قرنطینه | ✔ probe قرارداد آفلاین | ✖ orchestrator — نشست از سطح v1 شاخهٔ Bale (V-194) |
| حل گیرنده (ایتا) | ✔ | ✔ فقط‌خواندنی | ✔ (Fake) | ✖ — با حساب زنده بازبینی شود |
| حل گیرنده (بله) | ✔ (محدودیت مستند: بدون حل شماره) | ✖ عمداً بسته | نامعمول | ✖ |
| گفت‌وگوی عامل هوشمند | ✔ (adapter + محدودیت‌ها) | ✔ با آداپتور آزمایشی علامت‌دار | ✔ (Fake) | ✖ — نیازمند credential عامل واقعی |

## ۵. کارهای باقی‌مانده برای پذیرش زنده

1. صدور اعتبارنامهٔ سرویس توسط مدیر واقعی از پنل تنظیمات و تحویل امن آن به سامانهٔ آموزش (کمتر از یک دقیقه عملیات، توکن فقط یک‌بار نمایش داده می‌شود).
2. حساب ایتای زنده و روشن برای حساب مبدأ؛ سپس آزمون دستی `resolve → send-text` با یک گیرندهٔ مورد تأیید مالک.
3. تصمیم مالک دربارهٔ نوع حساب بله (Bot) و صدور توکن رسمی بات؛ تا آن زمان `bale_bot` fail-closed می‌ماند.
4. پیکربندی سرویس عامل واقعی (فروشنده/URL/credential) و پرچم قطع حالت آزمایشی؛ تا آن زمان پاسخ‌ها `is_test_response: true` دارند.
5. تصمیم مالک دربارهٔ سیاست شبکهٔ M2M در پروفایل استقرار (محدودسازی IP/مسیر داخلی در معمار انتشار).
