# گزارش اعتبارسنجی نهایی Eitaa Bridge UI MVP 6.1

## مبنا

- آرشیو ورودی کاربر: `eitaa_bridge_v0_7_ui_mvp6_0(2).zip`
- محصول نهایی: `0.7.0-ui-mvp6.1`
- بسته Bridge: `0.7.0.dev14`
- UI: `0.7.14`
- Core بدون تغییر: `0.6.0-core7.4.4` / `eitaa-core 0.6.0.dev18`
- SQLite schema: `8`

## اصلاحات قطعی

- پیام‌های موجود ابتدا از SQLite محلی خوانده می‌شوند و فقط در نبود داده، جلوتر بودن پیام سرور، کمبود پیام‌های خوانده‌نشده یا پایان TTL همگام‌سازی Remote انجام می‌شود.
- تغییر سایت مقصد WordPress، بازکردن Composer و پایان انتشار، دیگر Sync کامل پیام‌های ایتا را آغاز نمی‌کند.
- پس از انتشار WordPress، همان نمای محلی فعلی و تعداد پیام بازشده حفظ می‌شود؛ نمای تاریخی نیز فقط از SQLite تازه می‌شود.
- صفحه‌بندی پیام‌های قدیمی ابتدا از Cache محلی انجام و فقط در پایان Cache یک صفحه از سرور دریافت می‌شود.
- Thumbnail تصویر هنگام نمایش پیام دریافت و روی دیسک Cache می‌شود؛ تصویر کامل فقط با کلیک کاربر یا هنگام انتشار WordPress دریافت می‌شود.
- فایل کامل رسانه در `data/media/ui-cache/full` ذخیره و برای نمایش کامل و انتشارهای بعدی بازاستفاده می‌شود.
- رسانه‌های بزرگ از Endpoint محلی Stream می‌شوند و داخل JSON به Base64 تبدیل نمی‌شوند.
- Core در طول عمر API به‌صورت کنترل‌شده بازاستفاده می‌شود تا هزینه باز و بسته‌شدن مکرر Session و SQLite کاهش یابد.
- HTTP با تأیید صریح فقط برای localhost، IP خصوصی شبکه و دامنه توسعه محلی مجاز است؛ HTTP عمومی همچنان رد می‌شود.
- فرم سایت WordPress با ورودی سفید، Border تیره، متن روشن، Focus طلایی و توضیح واضح نام کاربری/Application Password اصلاح شد.
- دکمه آزمون اتصال ابتدا تنظیمات فرم را ذخیره و سپس همان سایت را آزمایش می‌کند.
- Runtime logger چرخشی، زمان پاسخ، وضعیت HTTP، کد خطا و Hit/Miss رسانه را بدون ثبت Secret یا Body نگهداری می‌کند.
- Launcher پیش‌فرض از Python و UI ازپیش‌ساخته‌شده در Microsoft Edge App Mode استفاده می‌کند؛ Electron و Node.js در اجرای روزمره لازم نیستند.
- سرویس سبک موجود بازاستفاده می‌شود؛ خطاهای راه‌اندازی در `runtime/logs/server-console.log` و گزارش‌های ساختاری در `runtime/logs/application.jsonl` قرار می‌گیرند.
- Builder اداره شامل `tzdata` و اصلاح دائمی حذف ناخواسته Packageهای داخلی `diagnostics` است.
- Migration اختصاصی MVP 6.0 داده‌های اصلی را با Backup منتقل می‌کند و Diagnostic/Logهای تاریخی حجیم را عمداً کپی نمی‌کند.

## مرز معماری

برای این نسخه هیچ کد Core یا پروتکل ایتا تغییر نکرد. امکانات لازم از API عمومی Core 7.4.4 استفاده می‌کنند. اصلاحات Cache، اولویت UI، Logger، WordPress، HTTP خصوصی و Launcher در Bridge/UI انجام شده‌اند.

## محدودیت‌های باقی‌مانده

- این محیط Linux نمی‌تواند فایل Setup نهایی Windows را Code-sign یا روی Windows پاک Acceptance کند.
- انتشار واقعی Eitaa → WordPress، Upload رسانه، ارتقا از داده واقعی و Office Portable باید یک بار با حساب و سایت واقعی کاربر آزمایش شوند.
- Application Password نمایش‌داده‌شده در گفت‌وگو باید لغو و با رمز جدید جایگزین شود.
