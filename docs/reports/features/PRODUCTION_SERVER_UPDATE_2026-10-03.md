وضعیت: `DEPLOYED / PUBLIC_WEB_VERIFIED / SHARED_STATE_PRESERVED`

## نتیجه

نسخهٔ جاری محصول روی `eitaa.farhangimaz.ir` با مسیر رسمی `publish-site` فعال شد.
release نهایی `20261003T094554Z-4594440618fe` است. منبع runtime، پایهٔ

بازنویسی نشدند و داده یا نشست رایانهٔ توسعه به سرور منتقل نشد.

## پیش‌بررسی و بسته

- پیش از عملیات، انتشار فعال متعلق به 2026-09-26 بود. دامنه با vhost واقعی و
  پاسخ عمومی HTTPS تأیید شد؛ Backend و gateway فقط روی Loopback بودند.
- سرویس‌های Nginx، ایتا، Docker، File Browser و proxy محلی فعال بودند. هشت
  کانتینر هم‌میزبان در حال اجرا و کانتینرهای دارای healthcheck سالم بودند.
- شش SQLite با `quick_check=ok` بررسی شدند. پیش از اولین فعال‌سازی، backup
  سازگار SQLite و کپی Config/محیط در پوشهٔ ریشه‌مالک `0700` و فایل‌های `0600`
  ساخته شدند؛ این پشتیبان در تلاش‌های بعدی بازنویسی نشد.
- بستهٔ نهایی ۳۶۶ فایل و ۱٬۶۱۸٬۷۰۳ بایت دارد. SHA-256 برابر
  `4594440618fee6e11f571de2ebbed0898c9caf055ebde6b6b4076f6fd3ec47be`
  است. نام امن فایل‌ها، منع operational state و hash محتوای هر فایل، در مبدا
  و مقصد تأیید شدند؛ یافتهٔ حریم خصوصی صفر بود.

## دو شکست و اصلاح

1. اجرای publisher با `umask 077` پوشه‌های نسخه و venv را بدون دسترسی گروه
   سرویس می‌ساخت. حذف دسترسی other کافی نبود؛ systemd در مرحلهٔ EXEC با
   Permission denied شکست خورد. بازگشت خودکار کد، نسخهٔ قبلی را سالم کرد.
   مجوز خواندن/عبور گروه اکنون صریح است، نوشتن گروه و همهٔ دسترسی‌های other
   بسته‌اند؛ import واقعی با کاربر سرویس پیش از تغییر symlink سنجیده می‌شود.
2. پس از رفع دسترسی، نصب تمیز با `ModuleNotFoundError: httpx` شکست خورد.
   محیط توسعه این وابستگی را داشت ولی `pyproject.toml` و `requirements.txt`
   آن را اعلام نمی‌کردند. ممیزی importها، `openpyxl` را نیز پیدا کرد؛ نسخه‌های
   آزموده‌شدهٔ `httpx==0.28.1` و `openpyxl==3.1.5` اعلام و wheel بازسازی شدند.
   آزمون تازهٔ import/اعلان و کنترل metadata بسته از تکرار این شکاف جلوگیری می‌کنند.

در تلاش دوم، Coordinator از schema ۷ به ۱۳ ارتقا یافت. بازگشت خودکار symlink
تنها کد قدیمی را برگرداند و آن کد با `coordinator_schema_newer` متوقف شد؛
بنابراین وقفهٔ موقت و پاسخ 502 رخ داد. بازیابی با انتشار نسخهٔ اصلاح‌شده به جلو
انجام شد؛ هیچ restore، downgrade یا حذف داده اجرا نشد. این محدودیت عمومی
rollback کد در F-111 باز است و در راهنمای Linux صریح شده است.

## پذیرش نهایی

- publication exit=0؛ سرویس active و هیچ unit شکست‌خورده‌ای وجود ندارد.
- hash همهٔ sourceهای runtime بسته با فایل‌های مقصد برابر و parity ماژول‌های
  نصب‌شدهٔ venv با source همان بسته کامل است؛ صرف تغییر source ملاک قرار نگرفت.
- hash Config و `.env` با پیش‌بررسی برابر است. شمار جدول‌های هویت، حساب و نشست
  حفظ و هر شش SQLite دوباره `quick_check=ok` شدند. AppUser و Multi-session
  روشن و Worker Process مطابق تنظیم پذیرفته‌شدهٔ قبلی خاموش باقی ماند.
- PID/وضعیت/شمار restart سرویس‌های دیگر و زمان شروع/health هر هشت کانتینر
  با پیش‌بررسی برابر است. Nginx reload، تغییر Firewall/Proxy یا listener تازه‌ای
  انجام نشد؛ syntax پیکربندی موجود Nginx نیز معتبر بود.
- عمومی با اعتبارسنجی معمول TLS: UI و readiness برابر 200، وضعیت AppUser برابر
  200 و unauthenticated، `/me` بدون نشست برابر 401، HTTP به HTTPS برابر 301
  و HSTS موجود است. hash دو JavaScript اولیه با build محلی برابر شد.
- سایت آزمون و File Browser با HTTPS پاسخ 200 دادند. timeout متناوب مشاهده‌شده
  برای سایت آزمون در بررسی مستقل بعدی به 200 رسید. خطای TLS دو vhost دیگر
  پیش از انتشار هم موجود بود؛ این سناریو تنظیم آن‌ها را تغییر نداده است.
- `pip check` در سرور بدون وابستگی شکسته و نسخه‌های دو کتابخانه مطابق اعلان‌اند.
  journal متعلق به invocation فعلی سرویس، ورودی warning/error ندارد؛ رخدادهای
  تلاش‌های قبلی با اجرای پذیرفته‌شده اشتباه گرفته نشدند.
  اجرای نهایی با `umask 077`، اصلاح دسترسی را در نصب واقعی پذیرفت؛ دسترسی other
  در فایل‌ها و پوشه‌های release صفر است.
