# گزارش بازنشانی کامل نصب سرور ایتا

تاریخ: 2026-09-26  
وضعیت: `DEPLOYED / SERVER_STATE_CLEARED / ADMIN_WEB_VERIFIED / EITAA_DIALOG_LIVE_PENDING`

## علت و محدوده

مالک حذف کامل داده‌ها و اعتبارهای قدیمی نصب سرور و جایگزینی با نسخهٔ محلی را صریحاً درخواست کرد. شاهد V-207 نشان می‌داد انتشار عادی `publish-site` کد را عوض می‌کند ولی `shared` را حفظ می‌کند. در بازبینی تازه، نصب سرور هنوز `worker_process.enabled=true` داشت؛ V-210 پیش‌تر ثابت کرده بود که UI v1 در همین حالت پیش از sync گفت‌وگو روی مسیر sites متوقف می‌شود و با خاموش‌کردن آن در نصب محلی ۲۰۶ گفت‌وگو بازیابی شده بود. بازبینی به‌سبب تغییر محیط، گزارش تازهٔ کاربر و درخواست صریح بازنشانی تکرار شد.

## بسته و پاک‌سازی

- منبع بسته: شاخهٔ محلی `Bale` روی commit `a8d10d92`، همراه با خروجی تازهٔ UI و فهرست گزارش‌های تولیدشدهٔ تازه. بسته ۷۰۷ فایل دارد و SHA-256 آن `3c562edee33e641c2fc438214c118d3979033737cdc187d31f437c2f0b362d64` است. اسکن نام‌ها در مبدا و مقصد، مسیر عملیاتی، `.env`، `bridge.json` واقعی، نشست و SQLite را در بسته صفر یافت.
- پس از توقف سرویس، هر ۱۳۵ فایل فضای `shared` قدیمی، شامل data، runtime، diagnostics، backups، catalog، Config واقعی و `.env` حذف شد. تنها Config تازه و `.env` خالی، با مالکیت و مجوز محدود سرویس، جایگزین شدند؛ هیچ کپی از state قدیمی برای rollback نگهداری نشد.
- Config تازه پروفایل HTTPS Reverse Proxy موجود را نگه می‌دارد، AppUser Auth، Multi-session و ورود پیام‌رسان از وب امن را روشن می‌کند و Worker Process را برای مسیرهای فعلی UI خاموش دارد. WordPress فقط placeholder بدون اعتبار دارد.
- بسته با مسیر رسمی `publish-site deploy eitaa-bridge` در release `20260926T163256Z-3c562edee33e` منتشر شد. در آغاز gate یک پاسخ گذرای 502 دیده شد؛ تلاش بعدی readiness و وضعیت ورود را پذیرفت. پس از پذیرش، ۹ release و ۸ receipt قدیمی حذف شدند و تنها release فعال ماند.
- یک مدیر تازه با رمز تصادفی تازه ساخته شد؛ هیچ اعتبار یا حساب قبلی منتقل نشد. نشست‌های ایجادشده در bootstrap و آزمون وب با `secure_delete` و `VACUUM` حذف شدند.

## اعتبارسنجی

- آزمون‌های هدفمند clean-install و HTTPS reverse proxy در منبع محلی گذشتند. TypeScript check، آزمون Observability، build رابط و کنترل یکپارچگی حافظه نیز گذشتند. check اسناد در ابتدا فقط به‌خاطر `REPORTS_INDEX.md` کهنه شکست خورد؛ generator اجرا و check نهایی سبز شد. یک invocation آزمون با نام فایل اشتباه پیش از اجرای درست هیچ تستی اجرا نکرد.
- در سرور، `publish-site status` سرویس را active و ready گزارش کرد. gateway برای readiness و AppUser status پاسخ 200 داد؛ قبل از bootstrap، `setup_required=true` بود. UI عمومی HTTPS نیز 200 بود.
- فایل باندل اصلی UI از مسیر عمومی با HTTP 200 دریافت شد و SHA-256 آن دقیقاً با build محلی برابر بود (`dd98f630b28df683672d98ffa8fa977eb70c55d279dc851b999454a058a5153e`).
- ورود وب مدیر تازه 200 و authenticated بود؛ وضعیت نشست احرازشده و فهرست حساب‌های پیام‌رسان هر دو 200 شدند. حساب پیام‌رسان صفر است. مسیر legacy sites بدون حساب، طبق مرز دسترسی حساب، 403 داد؛ این شاهد خرابی پس از انتخاب حساب نیست. پایگاه Coordinator اکنون یک مدیر و یک credential تازه، صفر PhoneAccount، صفر MessengerAccount و صفر AppUser session دارد؛ `PRAGMA quick_check=ok`. `.env` صفر بایت، فایل نشست و پشتیبان قدیمی صفر است.
- در پروژهٔ هم‌میزبان `onlineexam`، توکن اتصال ایتا که پس از پاک‌سازی قبلی دوباره ایجاد شده بود از `.env` پاک شد. کانتینر با source استقرار یافتهٔ آن پروژه به‌دلیل شرط اجباری قدیمی توکن unhealthy شد. source سرور طوری اصلاح شد که اتصال غیرفعال مجاز و توکن بدون URL نامعتبر باشد؛ آزمون قرارداد متناظر به‌روز، Docker image بازساخته و backend دوباره healthy شد. انتساب غیرخالی توکن در فایل و محیط کانتینر صفر است.

## مرز پذیرش و پیگیری

بازنشانی عمدی همهٔ گفتگوهای cacheشده را حذف کرد. تا مالک حساب ایتا را دوباره در UI اضافه و با کد ورود خود احراز نکند، نمایش گفت‌وگو ممکن نیست. پس از آن باید پاسخ sites/dialog sync و شمار گفت‌وگوهای DB، بدون خواندن متن پیام یا شناسهٔ مخاطب، به‌صورت Live سنجیده شود. حذف فایل‌های سرور به‌تنهایی نشست احتمالی نزد خود Provider را از راه شبکه ابطال نمی‌کند. اعتبارسنجی اصلاح‌شدهٔ `onlineexam` فقط در source فعلی سرور آن پروژه است و باید در منبع انتشار بعدی‌اش حفظ شود؛ اسکریپت پیکربندی آن نیز ممکن است توکن را دوباره بسازد.

تغییرات مستندی این Run تا پذیرش Live گفت‌وگوها در شاخهٔ محلی باقی می‌مانند؛ این سناریو هنوز شرط انتشار نهایی Git را ندارد.

هیچ OTP، ارسال پیام، انتشار WordPress یا انتقال نشست و دادهٔ لپ‌تاپ به سرور توسط Agent انجام نشد. هیچ رمز، توکن یا محتوای خصوصی در این گزارش ثبت نشده است.
