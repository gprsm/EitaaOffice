## Phase 10-C — نتیجهٔ preflight فقط‌خواندنی

هنوز فعال نشده است. موارد زیر صرفاً snapshot تاریخیِ محیط توسعه‌اند و طبق
تصمیم جدید کاربر blocker محسوب نمی‌شوند:

- رابط فعال: Wi-Fi با IPv4 `10.224.173.205/24`.
- Windows Network Category فعلی: Public.
- IP از DHCP دریافت شده و ثبات/رزرو آن تأیید نشده است.
- Rule با نام `Eitaa Bridge Trusted LAN` وجود ندارد.
- WordPress محلی در `http://localhost/wp-json/` در دسترس نیست؛ فقط وجود متغیرهای Credential تأیید شد و مقدار آن‌ها خوانده یا چاپ نشد.
- Coordinator فعلاً یک AppUser و یک MessengerAccount دارد.

اگر بعداً همین میزبان برای **پروفایل اختیاری LAN واقعی** انتخاب شود، checklist
همان استقرار شامل موارد زیر خواهد بود؛ این فهرست شرط شروع 10-C قابل‌حمل نیست:

1. کاربر تأیید کند Wi-Fi فعلی خصوصی و قابل‌اعتماد است، Guest network نیست و AP/Client isolation مانع ارتباط نیست.
2. برای IP سرور DHCP reservation یا IP ثابت معتبر ایجاد شود.
3. پروفایل شبکه با حضور و تأیید کاربر Private شود.
4. WordPress محلی فقط برای پذیرش واقعی integration توسط کاربر/مدیر سرویس اجرا و REST API قابل دسترس شود.
5. Pilot واقعی کاربر/حساب دوم فقط در صورت انتخاب پذیرش واقعی multi-user و با ورود/OTP خصوصی مالک حساب انجام شود.
6. Config دقیق LAN و Firewall محدود به IP/Port/Subnet فقط برای همان استقرار اعمال شود.

## الحاقیهٔ تصمیم استقرار — ۲۰۲۶-۰۸-۱۳

کاربر روشن کرد که مشخصات شبکهٔ رایانهٔ توسعه نباید شرط توقف توسعه یا
معماری محصول باشد. بر این اساس، موارد زیر دیگر blocker توسعه محسوب نمی‌شوند:

- Public بودن پروفایل Wi-Fi همین رایانه؛
- DHCP بودن IP همین رایانه و نداشتن reservation؛
- نبود Rule اختصاصی Windows Firewall در محیط توسعه؛
- خاموش بودن WordPress/Laragon، مگر در لحظهٔ آزمون واقعی integration.

10-C باید به‌صورت **پذیرش قابلیت حمل استقرار** ادامه یابد: پیکربندی از محیط
جدا باشد، Loopback و LAN اختیاری بدون تغییر کد کار کنند، و استقرار وب روی
HTTP/80 یا HTTPS/443 با پروفایل صریح و آزمون‌پذیر انجام شود. سرور داخلی فعلی
TLS را terminate نمی‌کند؛ بنابراین 443 باید پشت reverse proxy/TLS terminator
یا پس از افزودن یک پروفایل HTTPS مستقل استفاده شود. Bind کردن HTTP ساده روی
شماره‌پورت 443 به‌عنوان HTTPS پذیرفته نیست.

Pilot دوکاربره معیار اثبات جداسازی دو AppUser و دو MessengerAccount است، نه
شرط استفادهٔ عادی تک‌کاربره. آزمون خودکار/Fake باید در این فاز کامل بماند؛
Pilot واقعی دوحسابی می‌تواند تا محیط استقرار نهایی و حضور مالک حساب دوم تعویق
یابد. OTP، رمز دوم یا Credential حساب دوم نباید در گفتگو یا گزارش ثبت شود.
