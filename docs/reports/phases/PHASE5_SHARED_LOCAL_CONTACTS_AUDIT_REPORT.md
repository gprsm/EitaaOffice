# گزارش فاز ۵: دفترچهٔ محلی مشترک و قابل ممیزی

تاریخ تکمیل: ۲۰۲۶-۰۸-۰۲  
وضعیت: تکمیل‌شده، آزموده‌شده و آمادهٔ بررسی کاربر  
فعال‌سازی واقعی چندکاربره/چندحسابی: انجام نشده؛ Feature Flagهای نصب واقعی همچنان خاموش‌اند.

## هدف فاز

این فاز دفترچهٔ مخاطبان محلی موجود را به‌عنوان تنها دادهٔ مشترک میان AppUserها حفظ کرد و هم‌زمان مرز داده‌های واقعی پیام‌رسان را حساب‌محور ساخت.

قواعد نهایی:

- دفترچهٔ محلی میان AppUserها مشترک است.
- دسته‌های محلی نیز مطابق رفتار قبلی، مشترک باقی ماندند.
- شمارهٔ نرمال‌شده کلید یکتای مخاطب محلی است.
- ورود دوبارهٔ همان شماره رکورد تازه نمی‌سازد.
- نام‌ها و دسته‌ها طبق سیاست صریح `skip`، `update`، `replace` یا `merge` مدیریت می‌شوند.
- سازنده، آخرین ویرایش‌کننده، زمان‌ها و Revision هر مخاطب نگهداری می‌شوند.
- هویت مخاطب واقعی پیام‌رسان برای هر MessengerAccount در Binding مستقل ثبت می‌شود.
- افزودن مخاطب محلی به پیام‌رسان فقط با Runtime حساب انتخاب‌شده در سمت سرور انجام می‌شود.
- شناسهٔ حساب ارسالی در بدنهٔ درخواست قابل اعتماد نیست و در عملیات انتقال رد می‌شود.
- هیچ API فرضی برای بله ساخته نشد؛ فقط مرز Provider و فضای Binding برای افزودن آتی آن آماده شد.

## تصمیم معماری

پایگاه `data/contacts.sqlite3` همچنان منبع اصلی دفترچهٔ فعلی است. انتقال ناگهانی ۵۷۴ مخاطب واقعی به جداول رزروشدهٔ Coordinator می‌توانست نام کاربری، دسته، Source و سازگاری قابلیت‌های موجود را به خطر بیندازد؛ بنابراین همین Store با مهاجرت نسخه‌دار ارتقا یافت.

جداول رزروشدهٔ Coordinator دست‌کاری یا به‌عنوان منبع دوم فعال نشدند. این تصمیم از دو منبع حقیقت و مهاجرت ناقص جلوگیری می‌کند.

## مهاجرت Schema

نسخهٔ `CONTACT_SCHEMA` از ۱ به ۲ ارتقا یافت.

پیش از مهاجرت نسخهٔ ۱، SQLite Backup کامل با الگوی زیر ساخته می‌شود:

`contacts.schema1.<UTC timestamp>.<random>.bak.sqlite3`

تغییرات Schema:

- `contacts.created_by_app_user_id`
- `contacts.updated_by_app_user_id`
- `contacts.revision`
- Actorهای ساخت و ویرایش دسته‌ها
- جدول `contact_account_bindings`
- جدول append-only به نام `contact_audit_events`
- Indexهای Binding و Audit

مهاجرت داده‌های واقعی در این فاز عمداً اجرا نشد. وضعیت خواندنی نصب واقعی در پایان:

- Schema دفترچه: ۱
- تعداد مخاطب: ۵۷۴
- تعداد دسته: ۳

پس اولین اجرای نسخهٔ جدید، ابتدا Backup نسخهٔ ۱ را می‌سازد و سپس Schema را به نسخهٔ ۲ ارتقا می‌دهد.

## ادغام مخاطبان تکراری

- همهٔ شکل‌های رایج شمارهٔ ایران به کلید ثابت `+98...` تبدیل می‌شوند.
- همان شماره در چند قالب فقط یک مخاطب می‌سازد.
- اگر یک ردیف ورودی چند شماره داشته باشد و آن شماره‌ها قبلاً به چند رکورد جدا متصل باشند، در سیاست `update` رکوردها در یک تراکنش ادغام می‌شوند.
- دسته‌ها و شماره‌ها به رکورد برنده منتقل می‌شوند.
- Bindingهای حسابی بدون تبدیل‌شدن به Binding سراسری حفظ می‌شوند.
- `opt_out` هنگام ادغام محافظه‌کارانه حفظ می‌شود.
- تعارض قدیمی «شماره متعلق به یک مخاطب و Eitaa ID متعلق به مخاطب دیگر» همچنان Fail-closed است.
- اجرای هم‌زمان چند Upsert برای یک شماره فقط یک رکورد می‌سازد.

## Actor و Audit

Context تغییر فقط در سمت سرور ساخته می‌شود و شامل موارد زیر است:

- `actor_app_user_id`
- `messenger_account_id` انتخاب‌شده
- `provider`
- `request_id`

بدنهٔ درخواست نمی‌تواند سازنده یا ویرایش‌کننده را جعل کند.

رویدادهای ساخت، ویرایش، ادغام، بایگانی، تغییر دسته و Binding حسابی در زنجیرهٔ Hash ثبت می‌شوند. هر رویداد Hash رویداد قبلی را دارد؛ بنابراین حذف، جابه‌جایی یا تغییر رویداد قابل تشخیص است.

Metadata ممیزی فقط شامل شمارنده‌ها، سیاست‌ها، شناسه‌های داخلی و Reason Code امن است. شماره، نام، یادداشت، Access Hash یا Token در Metadata ممیزی ثبت نمی‌شود.

API جدید زیر Audit امن را برمی‌گرداند:

`POST /api/v1/contacts/audit`

شناسهٔ حسابی که با حساب انتخاب‌شده فرق دارد در پاسخ API ممیزی حذف می‌شود؛ در نتیجه مشترک‌بودن دفترچه باعث افشای شناسهٔ حساب دیگر نمی‌شود.

## جداسازی هویت پیام‌رسان

در حالت چندحسابی:

- `eitaa_user_id` و `access_hash` دیگر در رکورد مشترک نوشته نمی‌شوند.
- Provider Subject به شکل Fingerprint در Binding حساب انتخاب‌شده ثبت می‌شود.
- یک مخاطب محلی می‌تواند هم‌زمان Binding مستقل برای حساب A و حساب B داشته باشد.
- جست‌وجوی Eitaa ID فقط Binding همان حساب را می‌خواند.
- API دفترچهٔ مشترک فقط Binding حساب انتخاب‌شده را نشان می‌دهد.
- ستون‌های Legacy هویت ایتا در پاسخ چندحسابی پنهان می‌شوند.
- فقط حساب پیش‌فرض مهاجرت‌شده می‌تواند برای سازگاری خواندنی از Legacy Eitaa ID قبلی استفاده کند؛ حساب دیگر نمی‌تواند آن را ببیند یا Match کند.
- نوشتن `eitaa_user_id` یا `access_hash` از API عمومی دفترچه رد می‌شود.

## انتقال به پیام‌رسان انتخاب‌شده

Endpoint مستقل و Provider-neutral زیر اضافه شد:

`POST /api/v1/contacts/add-to-messenger/start`

رفتار آن:

- حساب مقصد فقط از Account Selector احراز هویت‌شده و Runtime سمت سرور گرفته می‌شود.
- `messenger_account_id` یا `account_id` داخل Body رد می‌شود.
- Job پس‌زمینه Actor، Correlation و Runtime همان درخواست را حفظ می‌کند.
- Endpoint سازگار قبلی ایتا باقی مانده است.
- افزودن تکی، افزودن دسته‌ها و ادامهٔ Import فایل همگی از حساب انتخاب‌شده استفاده می‌کنند.
- برای بله فقط `provider='bale'` و Binding/Adapter boundary آماده است؛ هیچ URL، Token flow یا Capability حدس زده نشده است.

## لاگ‌گذاری و حریم خصوصی

- `app_user_id` و `messenger_account_id` به رویداد درخواست API افزوده شدند.
- Actor و حساب به Jobهای پس‌زمینه منتقل می‌شوند.
- شمارهٔ کامل از رویداد خطای Import مخاطب حذف شد.
- خطاها فقط Contact ID داخلی، Error Code، Error Type، Job ID و شناسه‌های امن دارند.
- Audit دفترچه مستقل از لاگ عملیاتی و قابل Verify است.

این بخش ادامهٔ نظام لاگ‌گذاری فازهای ۳ و ۴-D است؛ بنابراین تأکید قبلی کاربر بر لاگ دقیق در فاز ۵ نیز اعمال شد.

## رابط کاربری

تغییرات رابط:

- اعلان روشن دربارهٔ مشترک‌بودن دفترچه و دسته‌ها
- Chip «مشترک» روی مخاطب محلی
- نمایش زمان آخرین تغییر
- نمایش وضعیت «در حساب انتخاب‌شده موجود است» فقط برای Binding همان حساب
- دکمهٔ «افزودن به حساب انتخاب‌شده» برای هر مخاطب
- انتقال دسته‌ها از Endpoint جدید Provider-neutral
- متن‌های Import و افزودن دستی به‌جای حساب ضمنی، حساب انتخاب‌شده را بیان می‌کنند

بررسی دیداری واقعی روی Preview کاملاً محلی انجام شد:

- دسکتاپ: موفق
- موبایل ۳۹۰×۸۴۴: موفق
- فرم، کارت مخاطب و دکمه‌های عملیات بدون هم‌پوشانی یا خروج از عرض
- Preview پس از بررسی بسته و دادهٔ موقت آن حذف شد.

## آزمون‌ها

فایل آزمون جدید:

`tests/test_phase5_shared_contacts.py`

پنج سناریوی مستقل اضافه شد:

1. Backup و مهاجرت Schema 1→2 بدون از دست‌رفتن داده
2. دفترچهٔ مشترک، Actorها، ادغام دسته و زنجیرهٔ Audit
3. ادغام چند رکورد و Upsert هم‌زمان
4. Binding مستقل یک مخاطب برای دو حساب و جلوگیری از نشت
5. دو AppUser، مشاهدهٔ دفترچهٔ مشترک، Runtime مستقل A/B و رد Account ID جعلی

نتیجه‌ها:

- آزمون‌های متمرکز مخاطبان و فاز ۵: ۲۰ از ۲۰ موفق
- Build رابط (`tsc` و Vite): موفق
- کل مجموعه به‌جز یک آزمون تاریخی: ۳۶۵ از ۳۶۵ موفق
- اجرای بدون حذف آزمون تاریخی: ۳۶۵ موفق و ۱ ناموفق

شکست تاریخی و نامرتبط:

`tests/test_runtime_ownership.py::test_windows_process_query_uses_explicit_utf8`

Fixture رشتهٔ لاتین `Documents\Eitaa` می‌سازد، اما Assertion پایان مسیر فارسی `Documents\ایتا` را انتظار دارد. این شکست پیش از فاز ۵ وجود داشته و به مخاطبان، Session یا تغییرات این فاز مربوط نیست.

هشدار Build:

- Vite فقط هشدار قدیمی بزرگ‌بودن Chunk اصلی بالاتر از ۵۰۰KB را نشان می‌دهد؛ Build ناموفق نیست.

## پیشنهاد برای فاز بعد

فاز بعد بهتر است «آزمون پذیرش سراسری و آماده‌سازی Rollout کنترل‌شده» باشد:

- اجرای Migration واقعی فقط پس از تأیید کاربر و مشاهدهٔ Backup
- تست دو حساب واقعی با دادهٔ آزمایشی کم و بدون ارسال انبوه
- کنترل نهایی گفتگو، مخاطبان واقعی ایتا، Cache، Job و Event در دو حساب
- بررسی Logout/Expiry واقعی A بدون اثر روی B
- سپس تصمیم جداگانه دربارهٔ API رسمی بله و Adapter آن
- فعال‌سازی Feature Flagها فقط پس از قبولی این آزمون‌ها

تا آن زمان، نسخهٔ فعلی از نظر کد آماده است ولی قابلیت چندکاربره/چندحسابی نصب واقعی عمداً خاموش باقی می‌ماند.
