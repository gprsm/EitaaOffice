# P1 — پروفایل فرستنده و قرارداد پایه

وضعیت اولیه: PLANNED. پیش‌نیاز: [قواعد مشترک](EXECUTION_RULES.md)، [برنامه](WEB_CLIENT_PROGRAM.md)، [دفتر وضعیت](EXECUTION_STATUS.md).

## مأموریت و محل تغییر

تنظیم انتخاب فرستنده را در محصول اصلی، در صفحهٔ حساب‌های سرویس، قابل استفاده کن. UI موجود ServiceAccountSettingsPanel و مدل/ذخیرهٔ service credentials و account registry را بررسی کن؛ داده‌های مجوز را دوباره در جدول موازی ناسازگار نساز. حساب باید شناسهٔ داخلی ثابت داشته باشد؛ شماره فقط نمایش ماسک‌شده برای مدیر است و کلید lookup عمومی نیست.

برای هر سرویس پروفایل هدف‌دار تعریف کن: حداقل otp و notification. هر پروفایل provider، account_id، enabled و revision دارد. هیچ حسابی صرفاً به دلیل اولین‌بودن در فهرست یا آخرین ورود، فرستندهٔ پیش‌فرض نشود. تنظیم پیش‌فرض باید انتخاب صریح مدیر باشد. پیشنهاد fallback فقط با سیاست صریح و فقط پیش از هر اثر جانبی/پس از شکست قطعاً بدون ارسال پذیرفتنی است.

## کار فنی الزامی

1. عضویت حساب در allowed_account_ids و Provider مجاز سرویس را در سمت سرور enforce کن. تغییر UI به‌تنهایی کافی نیست. scope ارسال، مشاهدهٔ status و عملیات مخاطب را جدا بررسی کن؛ نمایش messages.status در UI و قرارداد را با قابلیت واقعی هماهنگ کن.
2. ذخیرهٔ نسخه‌دار و اتمیک تنظیمات با کنترل revision پیاده کن. حساب حذف/آرشیو/غیرفعال یا مجوز لغوشده باعث unavailable شود؛ رکورد قدیمی نباید حساب دیگری را بی‌صدا جایگزین کند.
3. درخواست بیرونی فقط sender_profile_id/intent مجاز بدهد. account_id دلخواه به معنای دورزدن پروفایل نباشد؛ اگر قرارداد قدیمی account_id دارد، fence مالکیت و سازگاری آن را حفظ و سیاست مهاجرت را مستند کن.
4. انتخاب حساب در UI Provider-neutral باشد: ایتا و بله با account label امن و وضعیت واقعی ظاهر شوند؛ بلهٔ هنوز آماده‌نشده با دلیل فنی مشخص نمایش داده شود، نه ممنوعیت دائمی. تنظیم Bale Bot با Bale Personal مخلوط نشود.
5. schema، مسیرهای admin پیشنهادی، scopeهای نهایی، نمونه‌های ساختگی و خطاهای sender_not_configured/account_unavailable/stale_revision را در قرارداد ثبت کن؛ نام موجود را بدون بررسی تغییر نده.
6. قبل از تغییر مرکزی، regressionهای موجود F-090/F-091 و مسیر TTL/ظرفیت را اجرا کن. کد واقعی و شواهد با مبنای c513cdf3 تطبیق داده شوند؛ وجود commit دلیل صحت نیست.

## آزمون مستقل

- دو سرویس با حساب‌های مجزا و دو حساب هر Provider: انتخاب، ذخیره، reload و ارسال fake به همان حساب.
- حساب خارج از allowlist، پروفایل سرویس دیگر، credential بدون scope و Provider غیرفعال: رد پیش از worker؛ count ارسال صفر.
- رقابت دو ویرایش revision، حذف حساب انتخاب‌شده و درخواست با revision قدیمی.
- دادهٔ قدیمی بدون پروفایل: سیاست مهاجرت قطعی، بدون ارسال startup و بدون دستکاری bridge.json واقعی.
- UI و HTTP واقعی با fixture؛ متن نام/شمارهٔ آزمایشی غیرخصوصی. secret در response/DOM/log صفر.
- F-090/F-091: replay بدون فراخوانی آداپتور تازه، اختلاف متن conflict، expiry، ذخیرهٔ اتمیک، cancellation و inflight cleanup.
