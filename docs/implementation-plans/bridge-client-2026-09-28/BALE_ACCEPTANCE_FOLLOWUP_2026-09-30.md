# دستور اصلاحی دوم برای پذیرش آفلاین بله

> نتیجهٔ اجرای آفلاین V-252 (2026-09-30): S1 و S2 در source و آزمون‌های متمرکز اصلاح شدند. Child واقعی ۲۰۰۰ نتیجهٔ search را در ۲۰ صفحه با فریم‌های زیر ۳۵۰ kB بازگرداند؛ `complete` بدون توکن روی generation>1 رد شد. full Backend نهایی ۱۰۴۸ پاس/۱ skip و UI/wheel سبزند. پذیرش قطعی با ممیز/مالک است؛ دریافت خام WebSocket پیش از guard ۱۶ MiB کامل انجام می‌شود و B6 Live اجرا نشده است.

تاریخ: 2026-09-30؛ مرجع: F-099/V-251 و [دستور قبلی](BALE_ACCEPTANCE_REPAIR_2026-09-29.md). وضعیت: `OFFLINE_ACCEPTANCE_REOPENED / B6_LIVE_PENDING_INPUT`.

## دلیل بازشدن دوباره

اصلاح V-247/V-249 دو نقص V-246 را برای مسیر `contacts.query` با ۲۰۰۰ مخاطب مصنوعی و پاک‌سازی دیررسِ دارای توکن برطرف کرده است. نتیجهٔ آن آزمون‌ها معتبر است، ولی دو مسیر هم‌خانواده را نمی‌پوشاند:

1. `bale.provider.contacts.search` در `bale_provider_worker.py` همهٔ نتایج `search_contacts(query)` را در یک پاسخ IPC می‌فرستد. جستجوی فراگیر روی همان ۲۰۰۰ مخاطب با نام دقیقاً ۵۱۲نویسه‌ای، بدنهٔ حداقلی JSON برابر ۱٬۱۵۶٬۹۰۷ بایت می‌سازد؛ سقف IPC برابر ۱٬۰۴۸٬۵۷۶ بایت است. آزمون Popen فقط جستجوی یک مخاطب خاص را انجام می‌دهد. شمار ۵۰۰ در `contacts.query` نیز به‌تنهایی سقف بایتی فریم نیست.
2. `ProviderOperationReceiptStore.complete` وقتی `attempt_token=None` است، توکن ردیف فعال را بررسی نمی‌کند. پروب DB ایزوله: تلاش اول claim و release شد، تلاش دوم با generation=2 claim شد، سپس `complete(..., attempt_token=None)` همان ردیف تازه را `succeeded` کرد. مسیرهای فعلی orchestrator توکن می‌فرستند، اما قرارداد ذخیره‌گاه ادعای «تکمیل فقط با حصار تلاش» را تضمین نمی‌کند. آزمون موجود فقط توکن کهنه را رد می‌کند.

`git diff --check` در snapshot بازبینی exit=0 داشت؛ شکست قبلی V-246 در این نوبت تکرار نشد. این یافته‌ها شاهد آفلاین‌اند و هیچ حساب/نشست/شبکهٔ واقعی استفاده نشده است.

## دستور مستقیم به عامل

AGENTS، ترتیب حافظهٔ پروژه، F-099/V-246 تا V-251، دستور قبلی و گزارش V-249 را بخوان. درخت کاری dirty را حفظ کن؛ reset/checkout/clean یا تغییر فایل عملیاتی انجام نده. دو RED زیر را با آزمون مستقل کانونیکال روی مسیر واقعی محصول تثبیت و سپس اصلاح کن. پروب‌ها و آزمون‌های سبز V-247/V-249 را تضعیف نکن.

### S1 — کران‌داری همهٔ پاسخ‌های مخاطب در Child

- جستجوی فراگیر با دفترچهٔ مصنوعی بزرگ را از API اصلی تا Child واقعی (`subprocess.Popen`) اجرا کن. خطای فریم بزرگ را به‌صورت قابل‌تشخیص ثبت کن؛ هیچ متن/شمارهٔ خصوصی در خروجی آزمون نباشد.
- برای `contacts.search` قرارداد صفحه‌بندی/limit و `next_cursor` یا محدودیت صریح و قابل‌فهم بساز و آن را از Child، runtime، adapter، API و UI عبور بده. نتیجهٔ اضافی نباید به‌صورت موفق ولی ناقص ناپدید شود. جستجوی یک نتیجه‌ای پیشین همچنان کار کند.
- اندازهٔ **بایت** تمام فریم‌های خروجی مخاطبین، شامل query/search و پاسخ‌های خطا، پیش از نوشتن روی IPC کنترل شود؛ شمار آیتم به‌تنهایی کافی نیست. یک رکورد منفرد بیش از سقف نیز باید به خطای امن و صریح برسد، نه قطع Child یا پایان جعلی فهرست.
- `contacts.query` هنوز در هر صفحه `owner.list_contacts()` را کامل در Child می‌خواند؛ adapter در نبود `list_contacts_page` هم همین fallback را دارد. محدودیت حافظه/زمان این مسیر را بر اساس قابلیت واقعی BaleApi روشن کن: یا paging واقعی در منبع/رویکرد کران‌دارِ آزموده‌شده، یا اعلام صریح unsupported/limit. شواهد ۲۰۰۰ مخاطب فعلی فقط کران‌داری فریم query را اثبات می‌کند. `contacts.contains`، resolve و upsert نیز نباید برای عبور از این محدودیت نتیجهٔ غلط یا اثر ناخواسته بسازند.
- آزمون‌های adversarial: ۲۰۰۰ نتیجهٔ جستجوی یکسان با نام ۵۱۲نویسه‌ای، صفحهٔ آخر، صفر حذف/تکرار، دو حساب، cursor نامعتبر، نام/رکورد خیلی بزرگ، خطای امن، و کران بایتی همهٔ فریم‌ها. آزمون UI باید API و حالت «بیشتر» را مصرف کند؛ شبیه‌سازی دستی حلقهٔ API به‌تنهایی شاهد UI نیست.

### S2 — حصار تکمیل رسید در خود ذخیره‌گاه

- `complete` باید روی ردیف `in_progress` به تلاش فعال bind شود. در generation>1، توکن غایب یا کهنه نباید بتواند ردیف را terminal کند؛ در صورت نیاز، سازگاری رکوردهای تاریخی generation=1 را صریح و آزموده نگه دار.
- بررسی و UPDATE زیر همان تراکنش اتمیک باشند. فراخوانیِ دیررسِ تلاش قبلی، بدون توکن، با توکن نادرست و پس از restart را برای text/media/upsert/remove بیازما. تکمیل معتبر تلاش تازه، replay پایانیِ همان نتیجه، و عدم دست‌کاری terminal حفظ شود.
- تمام فراخوانی‌های production به `complete` را با توکن واقعی همان claim مرور کن؛ هر مسیر استثناییِ بدون توکن باید با دلیل ایمنی ثبت شود. خطای bookkeeping نباید به ارسال دوبارهٔ اثر نامعلوم منجر شود.

## دروازهٔ پایان

RED و GREEN مستقل هر دو مورد، پروب‌های قبلی، آزمون واقعی Child با جستجوی فراگیر و کنترل بایت، regressionهای دریافت/ارسال/حساب‌ها، full pytest، UI check/observability/build، wheel parity، `git diff --check` و کنترل‌های اسناد را روی snapshot ثابت ثبت کن. F-099، baseline، گزارش پذیرش و handoff را با دامنهٔ واقعی شاهد همسو کن. تا آن زمان «تنها B6 باز است» یا «پذیرش آفلاین کامل» ادعا نشود. B6 Live همچنان به ورودی و تأیید همان‌لحظهٔ مالک نیاز دارد؛ این دستور مجوز عملیات زنده نیست.
