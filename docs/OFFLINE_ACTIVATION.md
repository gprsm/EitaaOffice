# فعال‌سازی آفلاین وابسته به دستگاه

## تجربهٔ کاربر مقصد

در اولین اجرای نسخهٔ بسته‌بندی‌شده، پیش از شروع Backend یا بازشدن داده‌ها، پنجرهٔ «نسخه اختصاصی Eitaa Bridge» نمایش داده می‌شود. پنجره یک کد درخواست قابل‌کپی تولید می‌کند. این کد فقط fingerprint هش‌شده و نسخه‌دار دستگاه را حمل می‌کند و شامل Machine GUID یا شمارهٔ Volume خام نیست.

1. کاربر کد درخواست را برای مالک نرم‌افزار می‌فرستد.
2. مالک با ابزار خصوصی صدور مجوز، یک کد فعال‌سازی امضاشده می‌سازد.
3. کاربر کد فعال‌سازی را با دکمهٔ «جای‌گذاری از کلیپ‌بورد» یا منوی راست‌کلیک در همان پنجره Paste می‌کند. دکمه، `Shift+Insert` و میان‌برهای keycode-based به فارسی یا انگلیسی بودن layout کیبورد وابسته نیستند.
4. برنامه امضای Ed25519، Product، نسخهٔ fingerprint، زمان اعتبار و تطبیق دستگاه را کنترل می‌کند.
5. کد امضاشده با Windows DPAPI در `data\licensing\activation.dat` ذخیره می‌شود.

پس از فعال‌سازی معتبر، بررسی Startup بی‌صداست و کاربر پنجرهٔ دیگری نمی‌بیند. حذف، خرابی، کپی از Windows user دیگر یا ناسازگاری fingerprint باعث بازگشت به پنجرهٔ فعال‌سازی می‌شود؛ Provider، Config و Coordinator DB پیش از تأیید مجوز باز نمی‌شوند.

کدها برای تایپ دستی طراحی نشده‌اند. طول نمونهٔ request فعلی 258 و activation استاندارد حدود 563 نویسه است. یک format binary نسخه‌دار می‌تواند آن‌ها را تا حدی کوتاه کند، اما امضای Ed25519 به‌تنهایی حدود 86 نویسه Base64URL دارد. کوتاه‌سازی شدید به سرویس lookup آنلاین یا کاهش metadata/امنیت نیاز دارد؛ بنابراین RC4 برای سازگاری format را تغییر نمی‌دهد و Copy/Paste مطمئن را حل می‌کند.

## انتقال به رایانهٔ دیگر

مجوز برای ترکیب هش‌شدهٔ Machine GUID و serial دیسک سیستم صادر می‌شود و فایل ذخیره‌شده نیز به Windows user فعلی مقید است. بنابراین کپی پوشه یا Restore روی رایانهٔ دیگر مجوز قابل استفاده ایجاد نمی‌کند و رایانهٔ مقصد کد درخواست تازه می‌سازد. نصب مجدد Windows، فرمت/تعویض دیسک سیستم یا تغییرهای مشابه نیز می‌تواند نیازمند فعال‌سازی دوباره باشد.

Backup ممکن است فایل محافظت‌شدهٔ فعال‌سازی را همراه state محلی نگه دارد، اما این فایل روی دستگاه دیگر معتبر نمی‌شود. کد فعال‌سازی متن ساده نیز فقط برای fingerprint امضاشدهٔ خودش معتبر است.

## مدل امنیتی

- برنامه فقط کلید عمومی Ed25519 را حمل می‌کند؛ جعل مجوز بدون کلید خصوصی ممکن نیست.
- کلید خصوصی و ابزار مالک در customer Setup، Portable ZIP، source archive یا Git قرار نمی‌گیرند.
- رمزگذاری DPAPI مانع خواندن اتفاقی و کپی سادهٔ فایل مجوز می‌شود؛ امضای دیجیتال مرجع اصلی صحت است.
- درخواست فعال‌سازی هیچ شناسهٔ سخت‌افزاری خام را در UI، log یا گزارش آشکار نمی‌کند.
- مجوز می‌تواند دائمی یا دارای تاریخ انقضا، edition و featureهای امضاشده باشد.

هیچ قفل کاملاً غیرقابل‌شکست برای نرم‌افزاری که روی رایانهٔ تحت کنترل کاربر اجرا می‌شود وجود ندارد. مدیر محلی متخصص می‌تواند تلاش کند فایل‌های Python یا مسیر Startup را Patch کند. Code-signing، سخت‌سازی/کامپایل بخش verifier، integrity check و کنترل حقوقی می‌توانند هزینهٔ دورزدن را بالا ببرند، ولی ادعای «تضمین مطلق» درست نیست.

## کلید Branch و کلید Production

کلید فعلی فقط برای آزمون همین شاخه ساخته شده و خصوصی آن خارج از Repository و پوشهٔ تحویل قرار دارد. پیش از انتشار Production باید کلید Ed25519 رمزدارِ متعلق به مالک ساخته، public key آن در برنامه جایگزین و Setup نهایی دوباره Build/Test/Code-sign شود. private key باید نسخهٔ پشتیبان آفلاین و کنترل دسترسی مستقل داشته باشد؛ گم‌شدن آن صدور مجوزهای بعدی را ناممکن می‌کند.
